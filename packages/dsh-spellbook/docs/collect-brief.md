## 二、立论：「描述是承重墙，代码只是示例」

描述要说清四件事：

| 域 | 问的是 | 写在哪 |
|---|---|---|
| 是什么 | 效果长什么样、什么时候用 | 第一段 |
| **靠什么** | **机制** —— 迁移时唯一不能丢的那一句 | `==机制短语==` |
| 什么可变 | 哪些旋钮是设计选择，为什么这样选 | 描述后段 |
| **什么会失效** | 边界：什么情况下不成立、现象是什么 | `## 边界` |

### 价值门槛（这一条决定收不收）

**一句话就能说清的效果，不值得入库。**

- 值得收：金属箔、让离散属性也能过渡、文字绕图排、骨架屏扫光、变量字体的光学尺寸
- 不值得收：红色按钮、圆角卡片、三列布局、居中、加个阴影

要的是**非平凡的机制**，能迁移到别的场景去的那种。

### 硬门槛（五条，缺一不可）

跑得起来 / 记得住出处 / 说得清是什么 / 说得出场合 / 依赖透明。

### 零依赖

示例代码只用浏览器原生的 HTML/CSS/JS。**不引任何库、不引 CDN、不走构建**。

### frontmatter 各字段

| 字段 | 必填 | 取值 |
|---|---|---|
| `title` | ✓ | 中文标题 |
| `slug` | ✓ | 小写连字符，与文件名一致 |
| `category` | ✓ | `材质` / `动效` / `排版` / `交互` / `布局` / `图形` |
| `tags` | ✓ | **只能取自受控词表**，3–6 个，见下「标签」一节 |
| `since` | ✓ | `YYYY-MM`，这批统一写 `2026-10` |
| `source` | ✓ | 见下 |
| `when` | ✓ | 一句话：什么场合用 |
| `stage` | ✓ | `plain` / `photo` / `grid` / `dark` |
| `tier` | | 默认 `core`；浏览器支持还不广的写 `candidate` |
| `params` | | 需要滑杆时才写，见下 |

### 标签怎么写（必须取自词表）

标签不是关键词，是**筛选维度**。写词表以外的值，校验会直接拒收。

先跑一次，把值贴在眼前：

```bash
node scripts/tags.mjs
```

四个轴、约 205 个值：

| 轴 | 问的是 | 例 |
|---|---|---|
| 机制 `mech` | 靠什么做出来的（平台能力） | `backdrop-filter`、`mask`、`subgrid`、`feTurbulence` |
| 观感 `look` | 看起来像什么 | `玻璃`、`金属`、`发光`、`颗粒`、`图案` |
| 场合 `use` | 用在哪 | `表单`、`卡片`、`导航`、`加载`、`标题` |
| 触发 `how` | 什么让它动起来 | `悬停`、`滚动`、`拖拽`、`焦点`、`入场` |

规则：

1. **3–6 个**，不许重复。
2. **至少 1 个 `mech`** —— 每条咒语都得说得清靠什么成立。
3. **至少 1 个 `use` 或 `look`** —— 只说机制不说用途，等于没说这条是干什么的。
4. 机制挑**具体的那个属性**，不要挑笼统的家族：用 `backdrop-filter` 做磨砂就写它，
   不要写 `filter`；SVG 滤镜写 `svg-filter` 再加具体算子。
5. `look` 只在真是一种观感/材质时给；`how` 只在真有个触发源时给。
   一条讲 `text-wrap: balance` 的排版咒语不该有 `look`，静态材质没有 `how` 也很正常。
6. 词表里没有合适的值时，**挑最接近的现成值，不要自己造词** ——
   并在回报里说明是哪条、真实机制是什么。缺的词由维护者统一加进
   `shared/tags.mjs`，加一次全库都能用。

标签为什么这么严：这套词表建立之前，332 条咒语上挂着 631 个不同标签，其中 458 个
只出现过一次 ——「吸附」与「滚动吸附」并排、「SVG 滤镜」与「SVG滤镜」只差一个空格。
那种标签筛不了也数不出，等于没有。

### `source` 怎么写

代码是**你自己写的最小示例**，机制归属要老实交代：

- `机制来自 SVG feTurbulence 滤镜，自行实现`
- `机制来自 CSS 锥形渐变的硬色标，自行实现`
- `机制来自 HTML 规范的 popover 属性，自行实现`
- 若确实照某个开源项目的做法写，要写出项目名与许可证：`机制来自 miniMAC/magic（MIT），自行实现`

**不要**只写「自行实现」四个字而不交代机制出处。

### `stage` 怎么选（选错会出现「预览与描述不符」）

| 取值 | 什么时候用 |
|---|---|
| `photo` | 模糊、饱和、混合模式 —— 需要彩色背景才看得出来 |
| `dark` | 发光、阴影、半透明 |
| `grid` | 对齐、位移、跟随 |
| `plain` | 纯结构、对照用 |

**玻璃 / 模糊 / 发光类误用 `plain` 是最常见的错误。**

### `params`（可选，要滑杆才写）

```yaml
params:
  - { name: dur, label: 淡出用时, type: range, min: 0.2, max: 2, step: 0.1, default: 0.7, unit: s }
```

规则：`name` 必须**逐个**在代码里以 `var(--dur, 0.7s)` 的形式出现，且必须有回退值。
否则滑杆是假的，构建期会直接报错。不确定就别加 `params`。

## 四、注释与机制的硬规则

1. **描述里至少一处 `==机制短语==`。** 少了直接解析失败。
2. **每个代码块至少一处 `@mechanism` 注释。** 全文一处都没有会解析失败。
   机制短语与 `@mechanism` 注释要对得上 —— 描述说靠什么，代码就该在那里标出来。
3. `@mechanism` 后面**必须跟有信息量的说明**：

   - ✗ `/* @mechanism 这行很重要 */`
   - ✓ `/* @mechanism 原点放在底边，缩放时才是从下往上长 */`
   - ✓ `// @mechanism 只写变量，样式一律交给 CSS`

4. `## 边界` 是有效门槛：**与描述同等重要**。后面有测试会检查它存在，
   所以不要省。写「什么情况下会坏 + 为什么」。
5. `## 备注` 可选。

## 七、纪律

- **只创建你负责的 `content/effects/*.md`。** 不改任何已有文件，不改 `src/`、`shared/`、`scripts/`。
- **不要跑 `node build.mjs`，不要跑 `node scripts/vault.mjs rebuild`。**
  这两个会写数据库，多个工人同时跑会抢锁。自检只用 `scripts/check-file.mjs`。
- 不要做任何 git 操作。
- **不要为了验证去开浏览器、截图、或创建临时/脚本文件。** 验证只有一条路：
  `scripts/check-file.mjs`。示例代码的正确性靠你自己审读——**属性是否真存在、
  语法是否成立、机制是否真的由这几行承担**。写不存在的属性（比如
  `text-emphasis-size` 这种听着合理的名字）比写错更糟：它静默失效，
  读者会以为是自己用错了。拿不准的属性就换成你有把握的写法。
- 同批条目之间不要撞题：同一个机制换个角度写，或换一个机制。
- 数量不够时**宁可少写几条、每条都立得住**，也不要为凑数灌水。
  「一句话就能说清的效果」收了比不收更糟。
