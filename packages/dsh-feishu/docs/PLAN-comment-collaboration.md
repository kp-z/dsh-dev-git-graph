# 飞书评论协作实施计划

## 目标与边界

评论可靠同步到原绑定会话，不创建问答会话。负责人评论允许明确工作指令；其他人评论只答问题。AI 回复显示 `🤖:`，但防循环仅依据持久化的远端评论 ID，不依据正文前缀或账号。真实 @ 使用飞书用户 ID 与评论接口的 mention 协议。

本功能默认关闭，不修改现有真人任务以做试验。隔离测试应覆盖端到端采集、投递、回答与写回；真实飞书写操作只对明确标注的测试任务进行，未有测试任务时不宣称真实远端联调通过。

## 阶段一：接口与测试契约

计划：核对官方 SDK 评论 list/create/get 请求与响应；确认分页、作者 ID 类型、mention、回复关联与创建回执。检查 Host queue、guard 和会话事件；定义独立模块协议。

验收：有具体 API 证据；不能确认的协议不猜；只读检查不接触凭据。开始实现前由各负责者先报告计划。

## 阶段二：采集和唯一写回

计划：新增 comments.js 依赖注入协调器和独立持久化状态。首次完整扫描建立基线，之后按任务 ID + 评论 ID 去重；分页不完整不能前进。所有插件评论写回走统一入口，成功必须记录远端 ID；超时/未知结果冻结该任务自动处理并允许对账，不重复执行。

验收：多页、重复扫描、同账号真人评论、AI 回评正文变化、重启、失败中断、评论编辑均有 fake 测试。正文 `🤖:` 绝不参与判别。

## 阶段三：绑定会话与 UI

计划：复用 sessionController 的队列，不新建会话。未绑定、暂停、完成任务不投递；运行中等待。提供显式关联的评论回复工具，自动带作者 mention；非负责人处理期间用 Host guard 限制副作用工具，不影响后续负责人轮次。配置位于右上配置区，高级参数折叠；显示待处理/异常记录。

验收：处理评论不会回错任务；执行回执与发布状态分离；无 reply 权限或无法保护非负责人轮次时停止自动处理。旧宿主功能探针与测试兼容。

## 阶段四：回归与端到端

计划：完整离线测试与 fake bridge/Host/API 端到端；覆盖启动基线、新增评论、角色变化、暂停/解绑、写回未知、防自回复、工具越权和恢复。不直接运行可能改写真实飞书数据的旧联网 smoke。浏览器验证当前 GUI 配置。

验收：所有相关测试通过，失败已复核修复；报告区分 fake 全链路与真实远端验证。同步基础功能不被模型工作阻塞。

## 阶段五：提交发布

计划：审查 diff，仅 stage 本功能和本轮飞书 UI 改动，不包含其他插件或根目录已有改动。记录测试结果、限制和升级说明，commit 并推送当前分支，不 force push。

验收：提交与远端分支 hash 一致。运行中的 Host 不会因源码变化自动更新；新增文件需安装分发并按应用结果决定是否重启。
