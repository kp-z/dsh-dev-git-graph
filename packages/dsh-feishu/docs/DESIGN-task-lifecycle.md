# 任务生命周期与履约：需求对齐稿

> 一句话：**排期 = 到点往任务的会话里投一条指令**；任务的生命周期时间由系统自动打点；
> 真正给人看、用来衡量履约的是**预期完成时间**。
>
> 状态：**已实现（v0.11）**。§10 是上线前的真机验证记录；口径与实现一致，改代码前先改这里。

## 1. 术语

| 术语 | 含义 |
| --- | --- |
| 开工时间 `startAt` | 任务**第一次绑定会话**的时刻，自动记录 |
| 结束时间 `endAt` | 任务**被标记完成**的时刻，自动记录 |
| 预期完成 `expectedAt` | 人主动承诺的完成时间；履约评估的唯一基准 |
| 排期 `schedule` | 到点往会话投递指令的规则（一次性 / 重复） |
| 投递 `deliver` | 到点后的动作：把一条指令送进任务当前会话 |
| 履约 | 实际完成与「首次承诺」的偏差，以及过程中的重承诺记录 |

## 2. 时间轴

```
绑定会话           到点投递(可多次)              标记完成
   │                    │                        │
   ├── startAt          ├── schedule fires       ├── endAt
   │                    │                        │
   └──────── 进行中 ─────┴────────────────────────┘
                        ↑
                   expectedAt（承诺，可改；改一次记一条）
```

| 字段 | 产生方式 | 是否显示在插件卡片 | 是否写回飞书 |
| --- | --- | --- | --- |
| `startAt` | 绑定会话时自动 | **不显示** | 写「开始时间」 |
| `endAt` | 标记完成时自动 | **不显示** | 飞书原生完成时间即可，不另写 |
| `expectedAt` | 手动设置 / 一句话 / 工具 | **显示**（关键） | 可选，默认关（见 §4.3） |
| 排期 | 绑定会话后设置 | 显示 `⏱` | 不写 |

说明：

- 「绑定」包含两种：只绑定（`boundOnly`）与开工。二者都意味着**人已经把这条任务接到某条会话上了**，
  从这一刻开始算开始时间；不再区分「绑定时间 / 开工时间」。
- 结束时间只在**本地标记完成**（面板「完成」）或同步到飞书已完成时写入；飞书那边本来就有完成时间。
- `endAt` 与 `startAt` 只用于算周期与履约，不进卡片，避免卡片信息过载。

## 2.5 数据所有权：单一真相 + 投影

「双真相源」不是个好模型：同一个字段有两个写者，最后一定要回答「谁赢」，而这个问题没有稳定答案
（飞书的 `updated_at` 是**任务级**的，分不清改的是哪个字段）。正确的模型是：

> **本地事件流是唯一真相；飞书是它的投影，同时兼作人工输入口。**

先把每个字段的 owner 定下来：

| 数据 | owner | 本地怎么来 | 飞书怎么放 | 人在飞书改了怎么办 |
| --- | --- | --- | --- | --- |
| 开始时间 `startAt` | system | 「绑定会话」事件 | 原生 `start`（分钟级）+ 既有「开始时间」日期列（若存在，单向） | 不采纳：记 `external_edit`，面板提示，下次写回覆盖 |
| 结束时间 `endAt` | system | 「完成」事件 | 原生 `completed_at` + 既有「结束时间」日期列（若存在，单向） | 同上 |
| 预期完成 `expectedAt` | **human** | 事件 + 当前值 | 自定义**文本**字段「预期完成」，值 `YYYY-MM-DD HH:mm` | **采纳**：解析后当成一次人工输入，生成 `promise_changed` 事件；解析失败则忽略并提示 |
| 排期 `spec` | system | 事件 + 当前值 | 不落飞书 | —（飞书没有对应字段，不制造影子字段） |
| 履约指标 | derived | 按需计算，不落盘 | 不落飞书 | —（推导数据放两处必然漂移） |

远端变化怎么判定（不猜时间戳）：

1. 每次同步存一份「受管字段快照」（值 → hash）；
2. 写飞书前把这次写放进 **outbox**（记下期望值）；
3. 同步时远端值变了，只有两种解释：
   - **命中 outbox 且值等于我们写的** → 自己写的回声，忽略；
   - **不命中** → 人工输入：human-owned 采纳并记事件；system-owned 记一条 `external_edit` 后忽略或回写覆盖。

这样不会产生"冲突"，因为只有一个事件流：远端变化要么是回声，要么是一条新输入。
写失败也不会分叉：事件先落本地，outbox 重试，飞书只是**暂时落后于**本地，不会各说各话。

设计上的收益：真正双向可编辑的字段只剩 **1 个**（预期完成），冲突面被压到最小；
开始/完成是系统事实，人改了就按"系统所有"处理，不参与 merge 博弈。

## 3. 排期：一条链路，一个执行器

### 3.1 统一模型

排期只有一种对象（沿用现有 `state.schedules[taskId]`），到点后的动作统一为：

```
到点 → ensureSession(task) → 投递指令
```

`ensureSession` 是**一个函数**，会话来源由每条排期自己的 `delivery` 决定（默认 `session`）：

| delivery | 有会话 | 没会话 | 用途 |
| --- | --- | --- | --- |
| `session`（默认） | 投递到该会话 | **不触发**，面板标「未生效：没有会话」并给「绑定会话 / 改为到点新建」 | 绝大多数场景：提醒、推进 |
| `spawn` | 投递到该会话 | 新建会话再投递 | 旧的「按时执行 / 到点开工」等价物 |
| `auto` | 投递到该会话 | 新建会话再投递 | 明确想要「有就用、没有就建」的人 |

也就是说：**旧的「按时执行 / 到点自动开新会话」不是第二套规则，而是 `delivery = 'spawn'`
时同一条链路的表现**。飞书上「触发条件 = 按时执行 + 开始时间」的字段，同步时映射成
`delivery: 'spawn'` 的 schedule（`source: 'feishu'`）——字段本身就是「明确要求到点开工」，
所以老用户行为不变；而面板/工具新建的排期默认 `session`，不会静默多出会话。

### 3.2 投递内容

到点投递的 prompt = 现有的开工 prompt（任务档案 + 任务说明 + 提示），
开头加一行明确的指令头：

```
【定时指令 · 每天 09:30】继续推进这条任务（不是新任务，不要重复建会话）。
<原有开工 prompt 全文>
```

理由：模型拿到的信息和手动开工一致，行为不漂移；指令头让它知道这是定时触发，
避免它再问「要做什么」。

### 3.3 投递之后

- 成功：`lastFiredAt = now`，`runs += 1`，`lastReason = '已投递'`；任务状态不变（不新建、不改 started）。
- 失败：`lastAttemptAt = now`，5 分钟内不重试；`lastReason` 写明原因（会话不存在 / 宿主未就绪）。
- 一次性排期投递后失效；重复排期继续推进下一次。
- 任务完成 / 删除 / 解绑会话时，排期自动清理或标记失效（面板显示原因）。

## 4. 预期完成时间与履约

### 4.1 数据

```jsonc
// state.tasks[i] 上新增（本地权威）
{
  "expectedAt": 1793583000000,          // 当前承诺
  "promiseLog": [                        // 承诺变更历史（只增不改）
    { "at": 1793000000000, "expectedAt": 1793583000000, "kind": "set" },
    { "at": 1793200000000, "expectedAt": 1794000000000, "kind": "recommit", "reason": "等上游接口" }
  ],
  "delayLog": [                          // 延期（只记往后改）
    { "at": 1793200000000, "from": 1793583000000, "to": 1794000000000, "days": 4.8, "reason": "等上游接口" }
  ],
  "startAt": 1793000000000,
  "endAt": 0
}
```

派生（不落盘，按需算）：

| 量 | 公式 |
| --- | --- |
| 周期 | `endAt - startAt` |
| 偏差 | `endAt - expectedAt`（>0 延期，<0 提前） |
| 是否准时 | `endAt <= expectedAt` |
| 逾期中 | `!done && now > expectedAt` |
| 重承诺次数 | `delayLog.length` |

### 4.2 口径（关键，避免自欺）

- **延期以「首次承诺」为基准**：`firstPromise` = `promiseLog[0].expectedAt`。
  每次往后改承诺记为一次「重承诺」，单独统计；**不用它覆盖首次承诺**，
  否则把日期一直往后挪就能把延期洗成准时。
- 提前完成同样记账（正样本），用于看「承诺是否过于保守」。
- 逾期中进行中的任务算「风险」，不算延期；完成时才结算。
- 同一任务多次延期按「最后一次承诺 → 实际完成」算最终偏差，但「延期次数」照实累计。

### 4.3 写入位置

按 §2.5：`expectedAt` 的**唯一真相是本地事件流**，飞书字段是它的投影 + 人工输入口。

- 本地：`expectedAt` + `promiseLog` + `delayLog`，面板与工具直接读写，不等网络。
- 飞书：清单自定义**文本**字段「预期完成」，值固定格式 `YYYY-MM-DD HH:mm`（清单所在时区，默认 Asia/Shanghai）。
  为什么是文本不是日期字段：日期字段被服务端截断到天（§10 实测），而预期要精确到分钟；
  代价是飞书里不能按它排序/筛选——这个取舍已确认。
- 字段不存在时按需创建（每个清单一个，结果缓存进 `state.feishuFields`）；同名但类型不是 text 时
  不覆盖，降级为只本地并在面板提示。
- 写失败进 outbox 重试，**不影响本地承诺**，面板标「飞书未同步」；默认开
  （`settings.schedule.writeEtaToFeishu = true`）。
- 读回解析失败（有人在飞书里写成「下周三」）→ 不猜，记一条 warning，保持本地值。

### 4.4 指标

单任务（卡片上）：`预期 10-30 18:00 · 剩 2 天` / `逾期 1 天` / `提前 3 小时` / `延期 2 天`。

汇总（洞察卡新增「履约」块，纯本地计算）：

| 指标 | 说明 |
| --- | --- |
| 准时率 | 近 N 周完成的任务里 `endAt <= expectedAt` 的占比 |
| 平均偏差 | 完成任务的 `(endAt - expectedAt)` 均值（区分提前/延期） |
| 延期次数 | `delayLog` 新增条数（按周） |
| 逾期中 | 当前 `now > expectedAt` 且未完成的任务数 |
| 按工作区 / 优先级 | 哪类任务最容易延期 |

趋势按周聚合，写进现有 `state.metricsByDay` 的口径里（一天一行，便于外部跟踪）。

### 5.2 设置

| 项 | 默认 | 说明 |
| --- | --- | --- |

### 5.4 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/tasks/eta` | `{taskId, action: set\|clear, when?\|at?, reason?}` |

## 6. 整合方式（已定：一条链路 + delivery 三态）

结论：**不做全局开关，把「会话从哪来」做成每条排期的 `delivery` 字段**（见 §3.1）。

理由：

- 全局开关（A/B）只能二选一：默认关会让老用户飞书里写着「按时执行」的任务静默失效，
  默认开又会让新用户在没会话时被默默烧 token。
- 飞书字段本身就是一种「明确要求到点开工」的表达，映射成 `delivery: 'spawn'`
  既保住老行为，也不会污染面板新建的排期。
- 三种取值各自有明确语义，实现上仍然只有一个 `ensureSession` 和一个调度器，没有第二套流程。

默认与迁移：

- 面板/工具新建排期：`delivery: 'session'`（没会话时在配置阶段就拦住，并给两个明确选择：
  「先绑定会话」或「改为到点新建会话」）。
- 飞书「触发条件 = 按时执行」：`delivery: 'spawn'`。
- 旧本地排期：按 `source` 迁移（`feishu` → `spawn`，其余 → `session`）。
- 「没会话」时不产生静默失败：配置期拦住，已存在的标「未生效」并给一键处理。

## 7. 迁移与兼容

- 已有 schedule：保留规则；`source: 'feishu'` 的按 A/B 的口径决定是否触发。
- 已有任务：`expectedAt` 为空 → 卡片显示「设预期」，不参与履约统计。
- 首次上线不自动给人设预期（那等于替人承诺），只提示。
- `startAt`：历史任务没有这个值，用 `startedAt` 或绑定记录里的时间回填；都没有就留空。

## 8. 测试计划

- 纯函数：预期时间解析、准时/延期口径、首次承诺与重承诺的区分、逾期中判定。
- 集成：绑定 → 写 startAt/write-back → 排期到点 → 投递（有会话/无会话两种）→ 完成 → 履约结果。
- 面板：预期 chip 三态、完成态结果文案、逾期红色；排期在无会话时的提示。
- 真机：写回飞书「开始时间」「预期完成」字段各一次，读回确认。

## 9. 不做的事（本轮）

- 不做团队级履约排名（只看自己的）。
- 不做自动预估（模型猜一个预期）——承诺必须由人给。
- 不改飞书任务的原生截止时间语义。
- 不在卡片上展示开工/结束时间。

## 10. API 验证记录（2026-10-28 真机探针）

为了不在实现阶段才发现「字段建不出来 / 写不进去 / 读回来形状不对」，实现前用一次性探针
在临时清单上跑通了整条链路（清单和任务都已删除，账号里没有残留）。

| 项 | 结论 | 证据 |
| --- | --- | --- |
| 创建清单 | `POST /task/v2/tasklists`，body **扁平** `{name}` | code=0 |
| 创建 datetime 字段 | `POST /task/v2/custom_fields`，`{resource_type:'tasklist', resource_id, name, type:'datetime', datetime_setting:{format:'yyyy/mm/dd'}}` | code=0，返回 guid |
| 建任务 | `POST /task/v2/tasks`，body **扁平** `{summary, tasklists:[{tasklist_guid}], members:[…]}`（只有 PATCH 才是 `{task:{…}}`） | code=0 |
| 写 datetime 值 | `datetime_value` = **毫秒时间戳字符串**，语义是「该日期 UTC 00:00:00」 | 写入/读回都是 `1793232000000` |
| 写原生 start | `{start:{timestamp:'<ms>', is_all_day:false}}` + `update_fields:['start']` | 读回 `start_一致: true` |
| 一次 PATCH 同时写字段与 start | `update_fields:['custom_fields','start']` 可行 | code=0 |
| 同步链路读取 | `feishu-sync-cli task list` 返回的 `custom_fields` 带 `{datetime_value, guid, name, type}`，与 `customFieldValue()` 的取值方式一致 | 探针任务读回形状一致 |
| 清理 | 任务 `DELETE /task/v2/tasks/:guid`、清单 `DELETE /task/v2/tasklists/:guid` 都成功（字段没有删除接口，随清单不可见） | code=0 |

验证中发现的**硬约束**：

1. **日期字段只精确到天**（写入超过天的精度会被截断为 UTC 零点）。所以「预期 10-30 18:00」
   在飞书里只能显示成 `10-30`；**时分只存在于本地**。履约判定用本地精确值。
2. **`my_tasks` 只列「我负责的」任务**，且 CLI 默认最多 200 条（`max_items=200`）。
   不在其中的任务既不会同步、也不会有预期时间——这是现有同步口径，不扩大。
3. 字段创建后**没有删除接口**，只能从清单移出（`/custom_fields/:guid/remove`）；
   所以「自动建字段」要尽量一次建对，命名固定为「预期完成」，类型不匹配时降级为只本地。
4. 字段对**清单的所有协作成员可见**（这是权限模型决定的），预期时间一旦写进飞书就是团队可见的数据。

**粒度结论（已确认）**：飞书的任务自定义「日期」字段只到天，**包括 UI 里建的字段**
（用真实清单里已有的「开始时间」列实测：写 18:34 → 读回 00:00，探针任务已删）。
原生 `start` / `due` 是分钟级。所以「预期完成」改用**文本字段**承载 `YYYY-MM-DD HH:mm`。

### 第二轮探针（文本字段）

| 项 | 结论 |
| --- | --- |
| 创建 text 字段 | `{type:'text', text_setting:{}}` → code=0 |
| 写值 | `text_value: '2026-10-30 18:00'` → code=0 |
| API 读回 | `{guid, name:'预期完成', text_value:'2026-10-30 18:00', type:'text'}` |
| CLI 读回 | 同形状（`custom_fields` 里带 `text_value`），同步链路可直接用 |

### 第三轮：JS 全链路真机验证（v0.11 实现完成后）

用一条**临时清单 + 临时任务**（挂在自己名下，跑完删除）把宿主代码整条跑了一遍，而不只是桥接：

| 动作 | 结果 |
| --- | --- |
| 同步发现临时任务 | ✓（`my_tasks` 可见） |
| 设预期 `2026-11-03 18:00` | ✓ 写入文本列，`sync.ok=true` |
| 绑定会话 → 开始时间 | ✓ 原生 `start=13:31` + 「开始时间」日期列写当天 |
