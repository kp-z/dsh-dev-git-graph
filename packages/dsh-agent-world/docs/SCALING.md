# 面向大型游戏的扩展设计（R40 起的长期约束）

> 用户原话（R40）："我这个插件以后应该会进化成一个大型的游戏，里面的 subagent 会搭建在一个类似大型游戏的世界里，
> 所有各种东西都要留好余地扩展，而且各个模块都要解耦，以后升级换代好替换。"
>
> 这份文档回答三个问题：**已经做对了什么（不许退化）**、**到大型游戏会先在哪里撑不住**、**按什么顺序补**。
> 以后每一轮的设计都要能对上这里；对不上就先改这份文档，再写代码。

## 一、已经做到、且由机器强制的（不许退化）

| 能力 | 证据 | 守护 |
|---|---|---|
| 模块单向依赖 | `src/protocol/boundaries.ts` 的 `BOUNDARY_RULES` | `test/boundaries.test.js`（违规直接红） |
| 机制与内容分离 | 10 个内容库；R32 换整套场景配色只改一个内容文件，R20 换人物与家具只改内容包 | 内容校验 + "代码里零字面量"红线 |
| 渲染器可换 | 模拟只产出中立的 `ScenePlan`（D23），俯视 2D 与 three.js 3D 吃同一份 | `web/` 只许 import 协议层 |
| 会话后端可换 | 路由只认 `DialoguePort`；R37 把手写会话换成 agent-teams，路由一行没改 | `dialogueBackend` 配置切换 |
| 模拟确定、可回放 | `sim/domain/content` 禁用 `Date.now()`/`Math.random()`；外部事实以命令进 journal（D35/D41） | 红线扫描 + 1000 tick 确定性验收 |

这几条是"以后好替换"的地基。**任何新功能都必须走这些缝，不许绕开。**

## 二、到大型游戏会先撑不住的地方（按多早会碰到排序）

1. **智能的成本（最先碰到）**。现在每个说过话的角色都是一个常驻的 agent 会话。大型世界里成百上千个角色不可能每人一个模型会话——
   费用、并发、延迟都扛不住。**需要"智能分级"**：绝大多数角色由确定性模拟驱动，只有被玩家关注/被派活的少数被"唤醒"成真 agent，
   闲下来再"休眠"。这跟画面的 LOD（远处画简模）是同一个思路，只是对象换成了"脑子"。
2. **实体类型写死**。`Agent / Task / Message / Station / District` 是 `domain/types.ts` 里的固定接口。
   要加车辆、动物、物品、建筑、天气，每一样都得改领域类型、模拟、存档、渲染四处。**需要可注册的实体/组件模型**：
   新种类通过注册加入，核心不改。
3. **每 tick 遍历全部实体**。`movement / idle / interaction / scheduler` 都是 `for (const agent of world.agents)`。
   8 个角色没问题，几千个就会掉帧。需要**空间索引 + 只推进"活跃"的实体**（远处、闲着的按低频推进或冻结）。
4. **一个世界 = 一个场景**。`World.origin.scene` 只有一个。大型世界要**多区域**：区域独立加载/卸载、区域之间传送、只模拟玩家附近的区域。
5. **整世界一个 JSON 存盘**。`store/worldStore.ts` 每次写整份快照。世界变大后要**按区域/按块增量存**，事件 journal 也要能分段。
6. **3D 场景整块重建**。换 plan 时重建整个静态组，而且已知**每重建一次漏 16 张纹理**（M4-12）。大型场景需要**增量增删 + 资源引用计数 + 实例化渲染**。
7. **面板是单页手工拼的 DOM**。以后背包、地图、任务日志、设置……要能**按模块注册面板**，而不是都往 `main.js` 里接线。
8. **插件内部没有"模块注册表"**。现在所有子系统在 `src/index.ts` 里直接装配。要做到"某个模块整体替换"，需要一层**内部服务注册**：
   子系统按接口注册、按名字取用，换实现不改装配代码。

## 三、要补的扩展缝（决策见 ARCHITECTURE D42–D45）

| 缝 | 做法 | 替换时改什么 |
|---|---|---|
| **智能分级**（D42） | 角色有"脑"等级：`scripted`（纯模拟）/ `awake`（真 agent 会话）。唤醒/休眠由策略决定（被玩家点名、被派活、离玩家距离），有并发上限 | 换策略或换 agent 后端，模拟与面板不动 |
| **实体/组件注册**（D43） | 世界里的东西 = 实体 id + 一组组件（位置、外观、可交互、可工作……）；系统按组件处理。现有 Agent/Task 先**包成**组件，不一次性重写 | 加新种类 = 注册新组件 + 系统 + 内容库；核心不改 |
| **区域与按需模拟**（D44） | 世界分区域，每区域独立存盘与推进；只推进玩家附近/有活跃实体的区域，其余低频或冻结 | 换区域划分或存储后端，模拟规则不动 |
| **内部模块注册表**（D45） | 子系统（模拟、存储、对话后端、渲染、面板）都实现协议层接口，在一张注册表里登记；装配只按名字取 | 整体替换一个子系统 = 换一个注册项 |

## 四、顺序（每一步都要有可测的验收）

1. **先做压测**，用数字说话：造 500 / 2000 / 5000 个角色的世界，量每 tick 耗时、存盘耗时、3D 帧耗时、内存。
   没有这把尺子，后面的优化都是猜。验收：一张随规模变化的表，进 `docs/VERIFICATION.md`。
2. **智能分级**（D42）：它决定成本是否可控，而且直接建在刚做完的 agent-teams 套壳上（成员 = 唤醒的角色）。
3. **修纹理泄漏 + 增量渲染**（M4-12）：已知的确定缺陷，规模一大就爆。
4. **内部模块注册表**（D45）：把 `src/index.ts` 的手工装配换成注册表，给后面的替换铺路。
5. **实体/组件**（D43）与**区域**（D44）：动静最大，等压测告诉我们瓶颈具体在哪再动，避免过早设计。

**纪律**：每一步都保持第一节那张表全绿；不为"将来可能"写代码，只为压测或真实需求写代码——
但**接口先留好**，让将来要做的事不需要推翻现在的东西。
