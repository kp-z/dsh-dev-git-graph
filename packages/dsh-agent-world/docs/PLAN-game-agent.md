# PLAN — 让 dsh-agent-world 成为「AI 办公室」：好玩 · 稳定 · 易用

> 写于 R86（用户明确要求：组建智能体团队 + 每 2 小时一轮 + 规划如何把游戏与 AI 工作结合）。
> 本文件是**长期路线 + 每轮取活规则**。逐条任务仍进 `docs/BACKLOG.md`；
> 本文件只回答「往哪走、这一轮该做哪一件、谁做、怎么算做完」。

## 一、产品目标（一句话）

**让 AI 办公室真的能"监控 + 操控"智能体团队**：人在这里看得见谁在干什么、卡在哪，
并且能直接指挥；反过来，团队的真实工作（工单、会话、工具调用）在场景里**看得见、点得动**。
判据不是"画面好看"，而是：**看着这间办公室，能不能比看日志更快地知道团队状态，并做出下一步动作。**

三条支柱，任何改动都要能归到其中一条：
| 支柱 | 意思 | 反面（不要做） |
|---|---|---|
| **好玩** | 有反馈、有节奏、有因果（我点一下 → 世界有反应） | 纯装饰动效、无信息量的动画 |
| **稳定** | 不抖、不闪、不卡、不静默失败 | 靠"看起来还行"掩盖状态不一致 |
| **易用** | 一眼看懂、一步做到、无重复入口 | 同一功能做两份、按钮堆砌 |

## 二、界面重构（用户点名的四条）

### (a) 侧边栏整合 —— 看板从 Header 搬进侧边栏，**只留一份**

> **决策（已定，用户 R86 确认）**：侧边栏 = **页面内的 `<aside>`**，**不是** DSH GUI 的右侧栏 tab。
> 用户原话：「侧边栏最好是说的页面内的侧边栏」。
> 依据（`docs/RESEARCH-reuse.md` §0.A，已核实）：本插件的包**没有客户端半体**（`dsh.client = null`、
> 无 `lib/client.js`），挂 DSH tab 要先补一整套客户端 bundle + iframe 桥；而 iframe 里的列表
> **点不到父文档里的 Phaser 相机**——而「点列表 → 镜头聚焦」是本需求的核心，必须同文档。
> DSH tab 降级为**第二步可选**（BACKLOG M7-7），不阻塞本轮。

- 现状：`#board` 挂在 `header.topbar` 里（`web/index.html`），与页面其他信息挤在一行。
- 目标：**侧边栏 = 唯一的"人与团队"交互面**。侧边栏两档视图，同一个组件切换：
  - **Agent 列表**：谁在干什么（状态/工单/是否卡住）。
  - **任务流程图**：现有 `board.js` 的依赖图（不重写，搬进去复用）。
- 红线：**同一份渲染代码**，不许 header 与 sidebar 各写一遍（这正是用户说的"别做两份"）。
- 渲染方式（`RESEARCH-reuse.md` §0.B）：**复用 `board.js` 的 `createBoard()` 与 `renderMembers()`
  （board.js:363 已是"数组 → ul/li → 每行 click"）**，把它从"只在展开浮层里画"改成"给定容器就画"——
  **搬位置，不搬代码**；不引 React、不引新框架。
- 落点：新文件 `web/ui/sidebar.js` + `web/styles/sidebar.css`；`#board` 从 header 摘掉。
- ⚠️ **新增 `web/` 文件必须让它进 profile，否则整页会死**（BACKLOG **M10-14**，R89 实测踩中）：
  现象是 `main.js` 的 import 404 → 模块图整条失败 → **`__agentWorld*` 全局一个都没有**（页面看起来"加载完了"）。
  **`dsh plugin --profile web add file:$PWD` 并不可靠**（R89 实测：报 `+1 -32`，但新文件仍没进 profile，
  因为 pnpm 按路径缓存了包内容；而且它会顺手卸掉 32 个包）。
  **可靠做法 = 按 profile 的硬链接机制补链**：
  ```bash
  SRC=<pkg>/lib ; DST=~/.dsh/profiles/web/node_modules/dsh-agent-world/lib
  comm -23 <(cd $SRC && find . -type f | sort) <(cd $DST && find . -type f | sort)  # 列缺失
  # 逐个：mkdir -p $(dirname $DST/$rel) && ln $SRC/$rel $DST/$rel
  ```
  **纪律**：每次新增 `web/` 文件后，必须 `curl` 那个文件确认返回 **200** 再谈验证。

### (b) 列表聚焦 —— 点 Agent 卡片 = 镜头聚焦到它
- 现状：看板成员卡已能选中（`onMemberPick`），但没有"点列表 → 镜头过去"的统一入口。
- 目标：**任何 Agent 列表里的卡片，单击 = 选中 + 镜头平移到它**（复用已有 `selectAgent` 的跟随/平移动画）。
- 判据：点卡片后镜头 420ms 内平移到该 agent 居中；Esc 解锁。

### (c) 细节打磨 —— Map 任务显示 + Header 图标
- 工单在 Map/看板上的呈现（长标题截断、状态色、完成态弱化）。
- Header 图标：统一尺寸/间距/可点区域，去掉无信息量的装饰。
- 判据：1440×900 与 1024×768 下都不出现文字溢出与遮挡（沿用 M7-9 的裁剪判据）。

### (d) 交互简化 —— 调研 + 收敛
- 目标：**同类动作只有一条路径**。先调研再动手（见「取活规则」的 R1）。
- 候选：点人 = 选中（已做）；双击 = 打开对话？右键 = 快捷菜单？键盘 = 移动（已做）。
- 交付：一份 `docs/DESIGN-interaction.md`（含"为什么这样最好"的依据），再改代码。

## 三、稳定与"看得见"（与 UI 同等重要）

| # | 目标 | 判据 |
|---|---|---|
| S1 | **渲染不抖**：帧重置/动画互抢这类问题要有回归测试或页内自检 | 性能条 `切换 N` 长期不涨 |
| S2 | **状态一致**：客户端 world 与服务端快照不出现静默漂移 | `liveActors()` 与服务端逐字段一致 |
| S3 | **失败可见**：卡住的单/无工位/断流 → 界面上有明确出口（不是只看日志） | 造出 no-station 场景，界面报出来 |
| S4 | **分层正确**：墙体/家具/角色按 Y 排序穿插，不把实体塞进背景 | 与 Godot 原版对照截图 |

> 🔴 **S4 是当前用户抱怨最多的一条**（连续三轮提到：「这些办公桌都没有椅子」「不只是相对于其他 Agent，
> 还相对于桌子等元素」「椅子不应该在桌子上面」「桌子椅子和其他的电脑什么的是不是都要放到 Entity 里比较好」）。
> **优先级提到与 UI 同级**，排在侧边栏骨架之后立即做。

#### 决策：家具（桌/椅/电脑/黑板…）**是实体，不是背景**
用户的原话就是问句「是不是都要放到 Entity 里比较好」——**答案是要**，理由不是审美：
1. **Y 排序只有实体参与**。烘进背景的家具永远在所有角色之下，于是"人站在桌子后面"和
   "人站在桌子前面"画出来一样——俯视游戏的立体感全靠这一条。
2. **可交互性**（将来要点桌子看谁在用、点黑板看内容）要求它是独立显示对象。
3. **原版就是这么做的**（Godot 工程里家具与角色同层，靠 YSort 排序）。

落地判据（**逐项对照 Godot 原版，不许自己发挥**）：
- 家具进 `layers.entities`（与角色同层），`setDepth(depthFor(脚底 y / TILE_PX))`；
- **深度取脚底**，不是中心——"站在墙上方被墙挡、站在墙下方盖住墙"（与 `drawWalls` 同一套 `depthFor`）；
- 椅子 vs 桌子：椅子的脚底 y 更小就应被桌子挡——**当前"椅子在桌子上面"说明它的深度取错了**；
- 每件家具都要有截图对照（改前/改后 + 原版），不接受"看着差不多"。

## 四、团队与节奏

### 团队（Agent Teams）
| 角色 | 干什么 | 写什么 |
|---|---|---|
| **Leader**（我） | 拆活、指派、监督、**验收**、记账 | `docs/PROGRESS.md`、`docs/BACKLOG.md` |
| **designer** | 界面/交互设计 + 最佳实践调研 → 设计文档 | `docs/DESIGN-*.md`（**只写文档**） |
| **skill-finder** | 找可复用的现成方案（DSH 插件/skill、本地参考、Phaser 自带能力） | `docs/RESEARCH-reuse.md`（**只写文档**） |
| **developer** | 按设计文档实现 | `web/ui/sidebar.js`、`web/styles/sidebar.css`（**优先新文件**） |
| **reviewer** | 审实现：正确性、红线、回归 | 评审结论写进 `docs/PROGRESS.md` 的对应轮次 |

### 节奏
- **每 2 小时一轮**（`schedule` 定时投递）。一轮只做 **1 件**（最多 2 件）可验收的事。
- 一轮的固定流程：
  1. 读本文件「五、轮次计划」+ `docs/PROGRESS.md` 最上面一条；
  2. 取**第一个未完成**的轮次条目，确认它的依赖已满足；
  3. 按「谁做」指派；**没有可派的活就自己（Leader）做**；
  4. 做完**必须**留下可验证产出（代码+测试 或 文档+决策）；
  5. 写 `docs/PROGRESS.md`（做了什么/验证怎么跑/下一轮/假设/卡住），并更新本文件的勾选。
- **不接受**"只讨论不落地"。

## 六、协作纪律（**必须遵守**，否则会互相覆盖）

1. **同一个工作区有另一个 Agent 在并行开发**（他常改 `web/scene/scene-phaser.js`、`web/main.js`、
   `web/index.html`、`web/styles/layout.css`）。**动这些文件前先看 mtime**，优先**新建文件**。
2. **写文件前先 `read`**；遇到 `FS_STALE_VERSION` 就重读再改（说明有人刚动过）。
3. **每轮记下关键文件的 sha/大小**，否则"验证通过"验的是哪个版本都不确定。
4. 改完 `web/` 必须：`node --check` → `scripts/copy-web.mjs` → `tsc --noEmit` → 核对宿主吐出的文件。
5. **验证优先真机**（3080 + 页内 `__agentWorld*` 调试门面），不要只靠单测。
6. 每轮结束写 `docs/PROGRESS.md`，格式见文件头。
