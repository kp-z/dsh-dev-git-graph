## 零、先把一件好消息说清楚：图里要的东西**我们基本都有了**

用户给的参考图是 **DSH 内置的 Agent Teams 任务依赖图**（左：成员看板；右：DAG；下：详情）。
我把它的每个元素对着我们的世界数据核了一遍：

| 参考图的元素 | 我们的现状 |
|---|---|
| 成员看板（谁在做哪些任务） | ✅ `world.agents`（8 个角色 + `roster`/`role`） |
| 任务方框（`t1` `analyst` 标题） | ✅ `world.tasks` |
| **依赖连线（左→右：前置解锁后续）** | ✅ **`task.blockedBy` 已经有了**；`ready` 是**派生**状态，只在 `sim/ready.ts` 算一处（M1-5） |
| 绿=交付 / 红=失败 / 橙=验证 | ✅ `TaskStatus`：`done` / `failed` / `ready` / `blocked` / `in_progress` / `pending` |
| 详情栏的 "Unlocks t2, t3" | ✅ `blockedBy` 反向即得（**不用新数据**） |
| 底部的模型名 | ⚠️ 要等 M6（角色有 DSH 会话之后才有模型名） |
| **最后的 goal 是什么** | ❌ **没有这个概念——这是唯一要新增的东西** |

**结论**：看板（M7）**不是"再做一个子系统"，而是"把已有数据画出来"**。
这也是为什么它排在 M6 之后、却是**回报最快**的一件。

## 一、交互设计

### 1.1 心智模型：三层，每层只回答一个问题

| 层 | 回答的问题 | 主要界面 |
|---|---|---|
| **L1 总览** | "现在发生了什么？" | 3D 小镇 + 执行看板（M7） |
| **L2 选中** | "这个角色/这张单在干什么？" | 身份卡 / 工单卡（浮层，不离开场景） |
| **L3 对话** | "我要跟他说什么？" | 对话面板（侧栏）+ 头顶气泡 |

**规矩**：L2 永远是**浮层**，不跳页——因为用户要一边看小镇一边说话。
L3 打开时**场景不暂停**（小镇继续跑，这是"世界感"的来源）。

### 1.2 人物交互（L2）

| 操作 | 反馈 |
|---|---|
| 悬停角色 | 外发光描边 + 名牌（名字 + 职业） |
| **单击角色** | 选中（相机轻微聚焦）+ **身份卡**：名字/职业/当前状态（`AgentState`）/当前工单/情绪<br>三个按钮：**对话** · **跟随** · **看他的工单** |
| 双击角色 | 相机锁定跟随（再双击或 Esc 解除） |
| 右键角色 | 快捷菜单：**派一张单给他** · **让他去找某人** · 看对话历史 |
| 键盘 | `Tab` 在角色间循环 · `Esc` 取消选中 · `F` 跟随 · `Enter` 打开对话 |
| 悬停工单方框（看板里） | 3D 里对应工位/角色高亮（**看板与场景双向高亮**，这是看板存在的最大理由） |

**单击角色 = 选中，单击空白 = 取消**，与看板联动（看板里选中的角色方框同步高亮）。

### 1.3 对话设计（L3）——用户↔Agent

- **入口**：身份卡的「对话」、或直接点角色头顶的气泡图标、或 `Enter`。
- **形态**：右侧栏对话面板（像聊天）＋ 3D 里角色头顶显示**最近一句**的气泡。
- **时序**（已冻结在 `src/protocol/dialogue.ts`）：发送是同步的（`POST /api/say` 立刻返回
  `accepted`），回复是事件驱动的（SSE 的 `DialogueEvent`：`thinking` → `replied`/`failed`）。
  **面板不轮询、不阻塞**——R21 的教训：卡顿常常来自"在错误的层等了不该等的东西"。
- **thinking 必须可见**："他在想…"这个占位是**功能，不是装饰**：不显示它，用户会以为卡住了，
  再点一次，于是同一句话发两遍（还会建两个会话）。
- **失败要能下手**：模型没配置 / 会话创建失败 / 超时，各自给不同的、可下手的文案
  （沿用 R19 那条：灰蓝=加载中 / 品红=出错，宁可显示"他说不出话"，也不要装作没事）。
- **历史**：对话进事件流（D38），所以面板重开、换一个面板、甚至重放存档都能看到同一段对话。

### 1.4 对话设计（L3'）——Agent↔Agent（这一半更难，单独设计）

**核心取舍：谁跟谁说话由规则定，说什么由 LLM 定。**

| 阶段 | 设计 | 为什么这么分 |
|---|---|---|
| **M8-1 同站对话** | 两个角色落在**同一个站点**且都处于 `talking` 允许的状态时，`sim/` 触发一次对话（**谁、何时、几轮**都由确定性规则决定）；内容由两个 DSH Agent 轮流生成 | 保住确定性：`src/sim/` 里不许有 `Date.now()`/`Math.random()`。世界怎么变是规则的事，**说了什么**才是模型的事 |
| **M8-2 有界轮次** | 一次对话固定上限（例如 3 个来回），到点结束 | 成本可控，且不会两个模型互相刷屏 |
| **M8-3 结论落地** | 对话可以**产出后果**：一方可以调工具（`agent_world_dispatch` / `agent_world_claim`），于是"聊完真的去干活了" | 与 D35 一致：AI 只能通过工具改变世界 |
| **M8-4 主动发起** | 角色可以**主动**找某人（工具 `agent_world_talk_to(agentId)`），不再只由站点触发 | 更自然，但仍在同一条命令路径上，不破红线 |

**成本控制**（必须有）：只有**已唤醒**的角色参与对话；至少一方被唤醒才触发；
每次对话轮数有上限；被唤醒的角色数有全局上限（D36）。
**未唤醒的角色之间不自动对话**——否则 8 个角色会自己去叫醒彼此，成本失控。

**可视化**：对话进行时双方头顶**同时**出现气泡（一问一答，颜色区分谁在说）；
看板里两人的方框之间临时画一条**虚线**表示"正在交谈"。

### 1.5 控制与"让他们干活"（G4 的落点）

| 手段 | 交互 |
|---|---|
| **派单** | 拖一张工单到角色身上 / 选中角色后右键「派一张单给他」/ 在对话里说"你去修那个登录 bug" |
| **依赖可见** | 看板里点一张单 → 高亮它的**前置链与后续解锁**（参考图底部那句 "Unlocks t2, t3"） |
| **目标可见** | 看板顶部显示 **goal**（见 §3.4）与总体进度（参考图顶部的 `Delivered 25 / 4 failed / Waiting 0`） |
| **干预** | 暂停/继续（已有）· 加速/减速 · 手动把某个角色标为"卡住" |

**验收这句话**：对话里说"去修那个登录 bug" → **任务板真的出现这张单** + 角色真的走向工位。
判据是"**对话通过工具改变了世界**"，不是"画面变了"。

## 二、开发计划（按每小时的轮次切）

### 2.1 阶段划分

| 阶段 | 主题 | 里程碑 | 用户能看到的 |
|---|---|---|---|
| **P1** | 接上 AI 基座 | M6-0…M6-3 | 点角色 → 打字 → 他用自己的语气回话 |
| **P2** | **执行看板**（回报最快） | M7-1…M7-4 | 右侧出现成员看板 + 任务依赖图 + 详情 |
| **P3** | 让对话有后果 | M6-4 · M7-5 | 说一句 → 工单出现 → 角色动起来 → 看板进度更新 |
| **P4** | 角色之间也会说话 | M8-1…M8-4 | 两个人碰头聊起来，聊完各自去干活 |
| **P5** | 目标与复盘 | M7-6 · M6-6 | 顶部显示 goal 与进度；重开一局能回看上一局说过什么 |

**为什么 P2 插在 P1 与 P3 之间**：看板的数据**我们已经有**（§0），所以它是**最快能交付的可见成果**；
而且它反过来让 M6-4 可验证——"对话让世界变了"这件事，**看板上一眼就能看出来**。

### 2.3 每轮（每小时）的取法与顺序

1. 读 `docs/PROGRESS.md` 顶部「下一轮从哪继续」→ 取**依赖已满足**的最靠前 1–2 条；
2. 一条给一个队友（写盘范围不重叠），自己担共享契约与最终合并；

4. 记账 + 提交（只 `git add packages/dsh-agent-world`，**先 `git status --short` 确认暂存区**）。

**一轮做完不一条时**：把没做完的写回 BACKLOG 为 `ready`，并在 PROGRESS 里写清做到哪了。

## 三、执行过程与图表（看板设计）

### 3.1 一句话：**同一套视觉语言，不同的数据源**

用户给的那张图是 DSH **自己的** Agent Teams 看板（在 `app.asar` 里，是内置的，不是工作区插件）。
我们**不修改它**，而是**用它的视觉语言画我们世界的数据**——因为两者回答的是同一个问题：
"谁在做什么、卡在谁身上、离目标还有多远"。

### 3.2 座位（"直接抄它也可以"具体怎么抄）

工作区里已经有三个插件证明了这个挂法，**照抄它们**：

| 参考插件 | 抄什么 |
|---|---|
| `dsh-spellbook` | **右侧栏 tab** 的完整挂法（右侧栏一个 tab，点一下就把东西送进对话） |
| `dsh-dev-git-graph` | **"画一张图"**的范本（移植 vscode-git-graph：节点 + 连线 + 滚动 + 详情） |
| `dsh-daily` | 右侧栏 tab 的内容组织（列表 + 详情） |

**决定：一份渲染代码，两个宿主。**

| 阶段 | 看板挂在哪 | 理由 |
|---|---|---|
| **第一步（M7）** | **我们自己的 `/agent-world/` 页面里**，3D 场景旁边 | 与场景**双向高亮**才成立（点图里的单 → 3D 里工位亮）；数据直接从已有快照/SSE 来 |
| **第二步（M7-7）** | **DSH GUI 的右侧栏 tab** | 在对话时也能看；与内置 Agent Teams 图并排对照 |

两步**共用同一份渲染模块**（`web/board.js`：输入一份 `BoardModel` → 输出 DOM/SVG），
所以第二步只是"换个宿主 + 换个数据适配器"，不是重写。

### 3.3 看板形态（照参考图的三段式）

```
┌─ 顶部：进度 + goal ────────────────────────────────────────────┐
│ 目标：<goal 标题>   ███████░░░  Delivered 12 · 3 failed · 5 ready │
├─ 左：成员看板 ──┬─ 右：任务依赖图（左→右：前置解锁后续）──────────┤
│ verifier     t4 │  ┌t1──┐    ┌t2──────┐                          │
│  ● t4 ● t13     │  │analyst│──▶│dev-search│──▶ ┌t4 verifier┐     │
│ dev-search   t3 │  └──────┘    └────────┘     └──────────┘      │
│  ● t3 ● t8 ● t21│                                                │
│ dev-search ✗ t27│  （连线用淡色贝塞尔，别抢节点的视觉重心）        │
├─────────────────┴────────────────────────────────────────────────┤
│ 底部详情：t1 · <标题> · 状态完成 · 执行者 · 模型 · "Unlocks t2,t3" │
└──────────────────────────────────────────────────────────────────┘
```

**我们与参考图的三处不同（都是因为数据本来就不一样）**：

1. **节点上的"谁"不是抽象角色名，而是一个**真的在场景里走动的角色**——点方框，3D 里那个人发亮。
2. **状态色直接用我们已有的 `TaskStatus`**，不新造一套：`done` 绿 / `failed` 红 / `ready` 琥珀 /
   `in_progress` 蓝 / `blocked` 灰 / `pending` 更暗的灰。
3. **验证者不是一种"角色"，而是一种"站点能力"**：我们有 `Capability`（`code`/`review`/
   `research`/…）。所以参考图里的橙色虚线框 → 我们用在**需要 `review` 能力的任务**上。

### 3.4 `goal`——唯一要新增的概念（M7-6）

用户明确要"最后的 goal 是什么"。现在世界里**没有**这个概念。设计：

- **内容是内容**（D37/D31 同源）：新建内容库 `goals`（或给 `tasks` 条目加 `goal` 字段），
  形如 `{ id, title, description, tasks: string[] }`；`world.goalId` 指向当前目标。
- **它是派生视图，不是新状态机**：goal 的进度 = 它包含的任务的状态汇总。
  **不许**让 goal 自己有一套状态（那会和 `TaskStatus` 打架）。
- **顶部显示**：`目标：<title>` + 分段进度条（照参考图顶部的 `Delivered / failed / Waiting`）。
- 校验：goal 引用的任务 id 必须存在；**报错要给出可用取值**（沿用内容校验那条规矩）。

### 3.5 视觉规范（从参考图提取，照抄）

| 项 | 值 |
|---|---|
| 背景 | 深灰 `#121212`（跟随主题 token，别硬编码——我们有 `themes` 内容库） |
| 卡片 | 比背景稍亮 `#2C2C2C`，圆角 `6–8px`，1px 边框 |
| 主文字 / 次文字 | `#E0E0E0` / `#A0A0A0` |
| 成功 / 失败 / 验证 | `#22C55E` / `#EF4444` / `#F59E0B` |
| 边框语义 | 完成=实线深绿；**验证=虚线橙**；失败=实线红 + 微红底 |
| 连线 | SVG 贝塞尔，颜色 `#444`（**淡**，不抢视觉重心） |
| 字体 | 无衬线正文；**任务 id 与模型名用等宽** |
| 选中 | 微弱发光，区别于"高亮" |

**一条自我约束**：配色必须走 `themes` 内容库的 token，**不许在代码里写死十六进制**
（红线：配色是内容）。参考图给的是"目标值"，我们把它做成主题里的一组 token。

### 3.6 数据来源（**不用新接口**）

| 看板要的数据 | 从哪来 |
|---|---|
| 成员与他们在做什么 | `world.agents`（快照 + `agent.moved`/`agent.changed` 事件） |
| 任务与状态 | `world.tasks`（`task.changed` 事件已带 `reason`，含 `deps-done`） |
| **依赖边** | `task.blockedBy`（已有）；**列号 = 最长前置链**（纯函数，可单测） |
| Unlocks | `blockedBy` 反向索引 |
| 模型名 | M6 之后的 DSH 会话信息（可选显示） |
| goal | M7-6 新增 |

**所以 M7-1/2/3/4 可以**在 M6 完成之前就开工**——这也是把它排进 P2 的原因。

## 四、这一版 Roadmap 对已有计划的修正

1. **M7（看板）插到 M6-3 之后、M6-4 之前**：数据已有、回报最快、且它让 M6-4 可验证。
2. **M8（Agent↔Agent）排在 M6-4 之后**：它依赖"角色能调工具"，否则聊完没有后果，
   就只是个玩具。
3. **`web/` 迁 TS 提到 M7 之前**（P2 的前置）：看板要算"最长前置链"这类逻辑，
   手写 JS 没有类型会持续付代价（这笔债已经记了 11 轮）。
4. **M5-2（动作库）继续往后**：对话与看板是用户要的核心；角色动画是"更好看"。

## 五、红线（延伸自 GOAL.md 第五节，看板不例外）

1. AI 只能通过工具改变世界（D35）。
2. 人设/台词/配色/文案是**内容**，代码里不许字面量。
3. 对话与看板都**不许绕过事件流**做成私有通道（D38）。
4. `src/sim/`、`src/domain/`、`src/content/` 里不许 `Date.now()`/`Math.random()`——
   **看板的布局计算也要是纯函数**（列号、连线，都给得出同一份输入 → 同一份输出）。
5. 前端不许卡：看板加完要重新量一次（R21 的 `benchmark()` 与状态栏性能行）。
   **看板是纯 DOM/SVG，不进 3D 渲染循环**——这是它不会拖慢场景的前提。
